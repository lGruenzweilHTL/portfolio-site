Diffie-Hellman Schlüsselaustausch

⚠ Prüfung: Rechenaufgabe handschriftlich ohne Taschenrechner!
Grundprinzip

Diffie-Hellman löst das Problem der sicheren Schlüsselübertragung. Beide Seiten einigen sich auf öffentliche Parameter g (Generator) und mod (Primzahl). Jede Seite wählt einen geheimen privaten Schlüssel und berechnet daraus den öffentlichen Schlüssel.

Sicherheitsbasis: Modulare Exponentiation ist leicht zu berechnen, die Umkehroperation (diskreter Logarithmus) ist für große Zahlen praktisch unlösbar.

Ablauf (g=2, mod=29)
Beide einigen sich auf g = 2, mod = 29 (öffentlich)
Bob wählt privaten Schlüssel b = 10, berechnet B = 2¹⁰ mod 29 = 9 → sendet B=9
Alice wählt privaten Schlüssel a = 17, berechnet A = 2¹⁷ mod 29 = 21 → sendet A=21
Alice berechnet Shared Secret: Ba mod 29 = 9¹⁷ mod 29 = 4
Bob berechnet Shared Secret: Ab mod 29 = 21¹⁰ mod 29 = 4
Warum funktioniert das? (gb)a mod p = gb·a mod p = ga·b mod p = (ga)b mod p
Rechenbeispiel – 2¹⁰ mod 29 (Prüfungsaufgabe!)
Trick: Exponenten aufteilen! Man muss nicht 2¹⁰ = 1024 ausrechnen. Teile den Exponenten in Hälften.
Schritt 1: 2⁵ mod 29 = 32 mod 29 = 3 Schritt 2: 2¹⁰ mod 29 = (2⁵ mod 29) × (2⁵ mod 29) mod 29 = 3 × 3 mod 29 = 9 mod 29 = 9 ✓ Für 2¹⁷: 2¹⁷ = 2⁵ × 2⁵ × 2⁵ × 2² = 3 × 3 × 3 × 4 mod 29 = (9 × 3) mod 29 × 4 mod 29 = 27 mod 29 × 4 mod 29 = 27 × 4 mod 29 = 108 mod 29 = 21

Shared Secret Berechnung

Alice berechnet (9¹⁷ mod 29): 9² = 81 mod 29 = 23 23⁸ mod 29: 23² = 529 mod 29 = 7 7² = 49 mod 29 = 20 (=23⁴ mod 29) 20² = 400 mod 29 = 400 - 13×29 = 400-377 = 23 (=23⁸ mod 29) 9¹⁷ = 23⁸ × 9 mod 29 = 23 × 9 mod 29 = 207 mod 29 = 4 Bob berechnet (21¹⁰ mod 29): 21² = 441 mod 29 = 441 - 15×29 = 441-435 = 6 6⁵ mod 29: 6² = 36 mod 29 = 7 7² = 49 mod 29 = 20 (=6⁴ mod 29) 20 × 6 mod 29 = 120 mod 29 = 120 - 4×29 = 120-116 = 4 → Beide haben Shared Secret = 4 ✓
Effizienter Modexp-Algorithmus (Pseudocode)
func modexp(a, b, m):
    r = 1
    while b >= 1:
        if b mod 2 = 1:
            r = r * a mod m
        b = b div 2
        a = a * a mod m
    return r
02

RSA – Rivest Shamir Adleman

Grundlagen
  • Entwickelt in den 70er-Jahren
  • Sicherheit basiert auf Primfaktorzerlegung großer Zahlen
  • Anders als DH: Daten direkt mit Public-Key verschlüsseln
  • Entschlüsseln nur mit Private-Key möglich
Verwendung
  • Verschlüsseln von Daten (direkt, aber langsam)
  • In der Praxis: nur Session-Key verschlüsseln, dann AES
  • Digitale Signaturen (Unterschreiben)
  • Server-Authentifizierung bei TLS
Verschlüsselung mit RSA (Prinzip)

Alice verschlüsselt mit Bobs Public-Key. Bob entschlüsselt mit seinem Private-Key. Kein eigener Schlüssel vom Sender nötig (anders als DH).

Geheimschlüssel mit RSA übertragen (Hybrid)

RSA verschlüsselt nur den zufälligen AES-Key. AES verschlüsselt die eigentlichen Daten. So kombiniert man Sicherheit (RSA) mit Geschwindigkeit (AES).

RSA OpenSSL-Befehle (Referenz)
# Private Key erzeugen (2048 Bit)
openssl genrsa 2048 > priv.key

# Public Key exportieren
openssl rsa <priv.key -pubout > publ_bob.key

# Verschlüsseln
echo "Hallo Bob" | openssl pkeyutl -encrypt -pubin -inkey publ_bob.key > bob.txt

# Entschlüsseln
openssl pkeyutl -decrypt -inkey priv.key < bob.txt
03

Digitales Unterschreiben (Signatur)

⚠ Prüfung: Unterschreiben mit RSA + Hash + spezifischen Zahlen
Prinzip

Daten werden mit dem eigenen Private-Key verschlüsselt (= unterschrieben). Der Empfänger entschlüsselt mit dem Public-Key des Absenders → beweist Echtheit.

Wichtig: Nicht die Daten selbst signieren! Public-Key-Operationen sind langsam. In der Praxis wird nur der Hash (SHA-256) der Daten signiert!
Ablauf: Unterschreiben mit Hash
Sender Berechne Hash der Daten (z.B. SHA-256) → kurzer Fingerabdruck
Sender Verschlüssele Hash mit eigenem Private-Key → das ist die Signatur
Sender Schicke: Originaldaten + Signatur + (Public-Key / Zertifikat)
Empfänger Berechne Hash der empfangenen Daten selbst
Empfänger Entschlüssele Signatur mit Senders Public-Key → erhält Original-Hash
Empfänger Vergleiche beide Hashes → gleich = Unterschrift echt ✓
MD5 darf NICHT mehr verwendet werden! Wegen Kollisionen. Nur SHA-256 oder stärker verwenden.
04

POP3-Client Pseudocode

⚠ Prüfung: POP3 Client – alle Nachrichten abrufen (Pseudocode)
POP3-Protokoll Ablauf

Port: 110. Server antwortet mit +OK oder -ERR. Befehle: USER, PASS, LIST, RETR n, QUIT.

Vollständiger Pseudocode – alle Mails abrufen
// POP3 Client – alle Nachrichten abrufen
socket = new TcpClient()
socket.Connect("mailserver", 110)

rd = StreamReader(socket)
wr = StreamWriter(socket)   // AutoFlush=true, NewLine="\r\n"

// Greeting vom Server lesen
s = rd.ReadLine()           // "+OK POP3 server ready"

// Login
wr.WriteLine("USER uXX")
s = rd.ReadLine()           // "+OK"

wr.WriteLine("PASS geheim")
s = rd.ReadLine()
if not s.StartsWith("+OK"):
    print("Passwort falsch")
    return

// Mailanzahl ermitteln via LIST
wr.WriteLine("LIST")
s = rd.ReadLine()           // "+OK n messages"

nMails = 0
while true:
    s = rd.ReadLine()
    if s == ".":            // Punkt = Ende der Liste
        break
    nMails += 1

// Alle Mails einzeln abrufen
for i = 1 to nMails:
    wr.WriteLine("RETR " + i)
    s = rd.ReadLine()       // "+OK n octets"

    while true:
        s = rd.ReadLine()
        if s == ".":        // Punkt = Ende der Mail
            break
        print(s)            // Mail-Inhalt ausgeben

// Verbindung beenden
wr.WriteLine("QUIT")
s = rd.ReadLine()
socket.Close()

Transport Layer Security (TLS) & PFS

⚠ Prüfung: TLS mit PFS – Schritte kennen!
TLS ohne Forward Secrecy (alt)
Client sendet Connection-Request
Server sendet RSA-Public-Key (+ Zertifikat)
Client prüft RSA-Public-Key
Client erzeugt Session-Key, verschlüsselt mit RSA-Pub → sendet
Server entschlüsselt mit Private-Key
Problem Wenn Private-Key später kompromittiert wird, können alle aufgezeichneten Sessions entschlüsselt werden!
TLS mit Perfect Forward Secrecy (PFS)
Client sendet Request
Server sendet Zertifikat
Beide erzeugen temporäre DH-Keys
Server signiert DH-Public-Key mit RSA-Private-Key
Beide berechnen gemeinsamen Session-Key
Beide löschen DH-Keys sofort!
Security Choice Temporäre Schlüssel werden verworfen. Späterer Diebstahl des Haupt-Private-Keys gefährdet vergangene Kommunikation nicht.

Digitale Zertifikate

Was ist ein Zertifikat?

Ein Zertifikat ist eine von einer vertrauenswürdigen Stelle (CA) unterschriebene Public-Key/Name-Zuordnung. Es beweist, dass ein bestimmter Public-Key wirklich zu einer bestimmten Person/Domain gehört.

07

Authentifizierung mit Zertifikat

Ablauf
Server sendet Zertifikat (Public-Key + CA-Signatur)
Client prüft CA-Signatur mit CA-Public-Key
Client prüft DNS-Name + Gültigkeitsdatum
Server beweist Identität durch Signatur mit eigenem Private-Key
08

Zertifikat anfordern – Let's Encrypt & Certbot

ACME-Protokoll Challenge
Certbot erzeugt lokal Private-Key + CSR (Certificate Signing Request)
Certbot erstellt einen zufälligen String und legt ihn unter .well-known/acme-challenge/<token> ab
Certbot schickt CSR + Domainname an Let's Encrypt CA
CA macht HTTP-Request an die Domain, um den Token auszulesen
Token stimmt überein → Domainbesitz bestätigt → CA schickt signiertes Zertifikat zurück
09

Man-in-the-Middle Attacke

Szenario

Trudy fängt den Public-Key-Austausch ab, sendet stattdessen ihren eigenen Key an beide Seiten. Trudy entschlüsselt, liest mit, verschlüsselt erneut mit dem echten Key und leitet weiter.

Schutz Verwendung von vertrauenswürdigen Zertifikaten, SSH Host Fingerprints oder Pre-shared Keys.

Zufallszahlen

Entropiesammlung

Schnittstellen wie /dev/random sammeln Umweltrauschen (Maus, Keyboard, CPU-Temperatur) in einem Entropie-Pool, um kryptographisch sicheren Zufall zu garantieren.

Sichere Verwahrung

Smartcard Krypto-Chip

Der Private-Key wird auf der Smartcard generiert und verlässt diese niemals. Entschlüsselung und Signaturen finden direkt auf dem Chip statt, um Diebstahl durch Malware zu verhindern.

Andere Verfahren

DSA vs ECDSA

Elliptische Kurven (ECDSA, ECDHE) bieten die gleiche Stärke wie RSA/DSA, jedoch mit wesentlich kürzeren Schlüsseln und geringerer CPU-Last.
