Design Patterns Cheatsheet

Quick-reference notes for key design patterns, demonstrated in Java.

Singleton Pattern

Ensures that a class has only one instance and provides a global access point to it. Common use cases include managing database connection pools, global configuration settings, or hardware access controllers.

Key Advantages & Implementation Details This implementation utilizes the Bill Pugh Singleton technique. It relies on the JVM's lazy class-loading mechanism: the static nested class InstanceHolder is not loaded into memory until getInstance() is invoked. This guarantees absolute thread safety without runtime overhead from synchronized blocks. 
public class DatabaseConnection {
    // Private constructor prevents instantiation from other classes
    private DatabaseConnection() {}

    // Static helper class loaded only on-demand
    private static class InstanceHolder {
        private static final DatabaseConnection INSTANCE = 
            new DatabaseConnection();
    }

    public static DatabaseConnection getInstance() {
        return InstanceHolder.INSTANCE;
    }

    public void query(String sql) {
        System.out.println("Executing: " + sql);
    }
}
Factory Method Pattern

Defines an interface or abstract class for object instantiation, but defers the decision of which concrete class to instantiate to subclasses. This promotes loose coupling by eliminating direct instantiation calls like new ConsoleLogger() inside client code.

When to use Use this pattern when your system should be independent of how its products are created, or when you want to extend the framework by dynamically swapping concrete implementations without altering user-facing business logic. 
// Product Interface
interface Logger { void log(String msg); }

// Concrete Products
class ConsoleLogger implements Logger {
    public void log(String msg) { System.out.println(msg); }
}
class FileLogger implements Logger {
    public void log(String msg) { /* write to file */ }
}

// Creator (Factory)
abstract class LoggerFactory {
    public abstract Logger createLogger();
    public void logMessage(String msg) {
        Logger logger = createLogger();
        logger.log(msg);
    }
}
class ConsoleLoggerFactory extends LoggerFactory {
    public Logger createLogger() { return new ConsoleLogger(); }
}
Abstract Factory Pattern

Provides an interface for creating families of related or dependent objects (e.g. Buttons, Checkboxes, Windows) without specifying their concrete classes. Ensures that the client code only interacts with interfaces and receives consistent component themes.

Difference from Factory Method While Factory Method delegates instantiation of a single product to subclass overrides, Abstract Factory aggregates multiple factory methods to produce a unified suite of related objects. 
// Abstract Products
interface Button { void paint(); }
interface Checkbox { void toggle(); }

// Abstract Factory Interface
interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

// Concrete Family 1 (Windows UI)
class WinFactory implements GUIFactory {
    public Button createButton() { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}

// Concrete Family 2 (Mac UI)
class MacFactory implements GUIFactory {
    public Button createButton() { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}
Observer Pattern

Defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

Characteristics Subject maintains a list of observers and notifies them directly. Great for reactive UIs or data-binding, but can lead to tight coupling where the subject knows about the interface of its observers. 
import java.util.ArrayList;
import java.util.List;

interface Observer {
    void update(String state);
}

class Subject {
    private final List<Observer> observers = new ArrayList<>();
    private String state;

    public void attach(Observer o) { observers.add(o); }
    public void detach(Observer o) { observers.remove(o); }

    public void setState(String state) {
        this.state = state;
        notifyObservers();
    }

    private void notifyObservers() {
        for (Observer o : observers) {
            o.update(state);
        }
    }
}
Publisher-Subscriber Pattern

An architectural variant of the Observer pattern. Introduces an intermediate Message Broker or Event Bus, decoupling publishers and subscribers completely.

Key Differences Publishers do not know who the subscribers are (and vice-versa). They only communicate through a specific topic or event channel on the bus, allowing for highly scalable and asynchronous distributed systems. 
import java.util.*;

// Message Broker / Event Bus
public class EventBus {
    private static final Map<String, List<Subscriber>> topics = new HashMap<>();

    public static void subscribe(String topic, Subscriber sub) {
        topics.computeIfAbsent(topic, k -> new ArrayList<>()).add(sub);
    }

    public static void publish(String topic, Object message) {
        List<Subscriber> subs = topics.get(topic);
        if (subs != null) {
            for (Subscriber sub : subs) {
                sub.onMessage(topic, message);
            }
        }
    }
}

interface Subscriber {
    void onMessage(String topic, Object data);
}
Repository Pattern

Mediates between the domain and data mapping layers using a collection-like interface for accessing domain objects. It isolates the domain model from underlying data access technology (like SQL, NoSQL, or memory stores).

Design Goal By defining the Repository as an interface, the business logic remains mockable and independent of DB configurations. Mock databases can be easily substituted in unit tests. 
import java.util.Optional;
import java.util.List;
import java.util.ArrayList;
import java.util.Map;
import java.util.HashMap;

// Entity representing Domain Model
class User {
    private final String id;
    private String email;
    public User(String id, String email) { this.id = id; this.email = email; }
    public String getId() { return id; }
    public String getEmail() { return email; }
}

// Repository Interface defining the storage contract
interface UserRepository {
    void save(User user);
    Optional<User> findById(String id);
    List<User> findAll();
    void deleteById(String id);
}

// In-Memory Repository Implementation for rapid prototyping / testing
class InMemoryUserRepository implements UserRepository {
    private final Map<String, User> db = new HashMap<>();

    public void save(User user) { db.put(user.getId(), user); }
    public Optional<User> findById(String id) { return Optional.ofNullable(db.get(id)); }
    public List<User> findAll() { return new ArrayList<>(db.values()); }
    public void deleteById(String id) { db.remove(id); }
}
Model-View-Controller (MVC) Pattern

Splits user interface development into three distinct concerns: the Model (rules/data), the View (rendering visual layouts), and the Controller (handling user interactions and updates). This separation simplifies testing and increases code modularity.

Flow of Control User interacts with the View (or triggers an API endpoint) → Controller intercepts request → Controller updates the Model → Model alerts change or Controller coordinates feeding updated Model data back to the View. 
// Model: Represents raw state and business rules
class Task {
    private String title;
    private boolean completed;
    public Task(String t) { this.title = t; }
    public String getTitle() { return title; }
    public boolean isCompleted() { return completed; }
    public void setCompleted(boolean c) { this.completed = c; }
}

// View: Renders output for presentation
class TaskView {
    public void displayTask(Task task) {
        System.out.println("Task: " + task.getTitle() + 
                           " | Status: " + (task.isCompleted() ? "Done" : "Pending"));
    }
}

// Controller: Intermediary executing commands
class TaskController {
    private final Task model;
    private final TaskView view;

    public TaskController(Task model, TaskView view) {
        this.model = model;
        this.view = view;
    }

    public void completeTask() {
        model.setCompleted(true);
    }

    public void updateView() {
        view.displayTask(model);
    }
}
