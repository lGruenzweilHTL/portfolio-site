Serialization & DB Cheatsheet

Quick-reference notes — H2 database · JDBC resources · prepared statements · Serializable · object streams

What is H2

H2 is a lightweight, pure-Java SQL database. It can run fully in-memory (data lost on JVM exit), as an embedded file-based database, or as a standalone server — making it popular for tests, prototypes, and small desktop apps.

In-memoryjdbc:h2:mem:testdb
In-memory (kept alive across connections)jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1
Embedded filejdbc:h2:./data/mydb
Server modejdbc:h2:tcp://localhost/~/mydb

String url = "jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1";

try (Connection conn =
         DriverManager.getConnection(url, "sa", "")) {
    System.out.println("Connected: " + !conn.isClosed());
}
Schema setup with Statement
try (Connection conn = DriverManager.getConnection(url, "sa", "");
     Statement stmt = conn.createStatement()) {

    stmt.execute("""
        CREATE TABLE IF NOT EXISTS employee (
          id    INT AUTO_INCREMENT PRIMARY KEY,
          name  VARCHAR(100) NOT NULL,
          email VARCHAR(150) UNIQUE
        )
    """);
}
H2 Console H2 ships with a browser-based admin UI (org.h2.tools.Server.createWebServer().start() or the bundled h2-*.jar) for inspecting an in-memory or file database visually while debugging.
Why it matters for JDBC

Connection, Statement, PreparedStatement, and ResultSet all implement AutoCloseable and hold native/DB resources (sockets, cursors). Forgetting to close them leaks connections — try-with-resources closes them automatically, even if an exception is thrown.

try (Connection conn = DriverManager.getConnection(url, user, pass);
     PreparedStatement ps = conn.prepareStatement(
         "SELECT * FROM employee WHERE id = ?");
     ) {
    ps.setInt(1, 42);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getString("name"));
        }
    }
} catch (SQLException e) {
    e.printStackTrace();
}
Close order

Resources declared in a try-with-resources header are closed in reverse declaration order — last opened, first closed — mirroring manual nested try/finally blocks.

try (Connection c = ...;     // closed 3rd
     PreparedStatement ps = ...; // closed 2nd
     ResultSet rs = ...) {        // closed 1st
    // use rs
}
Suppressed exceptions

If the try block throws and a resource's close() also throws, the close-time exception is attached as a suppressed exception on the original — both are visible via getSuppressed(), nothing is silently lost.

catch (SQLException e) {
    for (Throwable s : e.getSuppressed()) {
        System.out.println("Suppressed: " + s);
    }
}
Why use PreparedStatement over Statement
StatementPreparedStatement
SQL built via string concatenationSQL parsed once, with ? placeholders
Vulnerable to SQL injectionParameters are escaped/typed automatically — injection-safe
Re-parsed/re-planned every callCan be precompiled and reused efficiently
No native binary/date handlingType-safe setters (setInt, setDate, ...)
Never do this "SELECT * FROM users WHERE name = '" + userInput + "'" — always use ? placeholders with a PreparedStatement instead of concatenating user input into SQL.
INSERT with parameters
String sql = "INSERT INTO employee (name, email) VALUES (?, ?)";

try (PreparedStatement ps = conn.prepareStatement(
        sql, Statement.RETURN_GENERATED_KEYS)) {

    ps.setString(1, "Ada Lovelace");
    ps.setString(2, "ada@example.com");
    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            int newId = keys.getInt(1);
        }
    }
}
Batch updates
String sql = "INSERT INTO employee (name, email) VALUES (?, ?)";

try (PreparedStatement ps = conn.prepareStatement(sql)) {
    for (Employee e : employees) {
        ps.setString(1, e.getName());
        ps.setString(2, e.getEmail());
        ps.addBatch();
    }
    int[] results = ps.executeBatch();
}
Querying & mapping a ResultSet
String sql = "SELECT id, name, email FROM employee WHERE name LIKE ?";

try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, "A%");

    try (ResultSet rs = ps.executeQuery()) {
        List<Employee> result = new ArrayList<>();
        while (rs.next()) {
            result.add(new Employee(
                rs.getInt("id"),
                rs.getString("name"),
                rs.getString("email")
            ));
        }
    }
}
The Serializable marker interface

java.io.Serializable has no methods — it's a marker interface that tells the JVM a class's instances may be converted to/from a byte stream. Without it, ObjectOutputStream throws NotSerializableException.

import java.io.Serializable;

public class Employee implements Serializable {

    private static final long serialVersionUID = 1L;

    private int id;
    private String name;
    private transient String cachedToken; // excluded from serialization

    // constructors, getters, setters ...
}
serialVersionUID

A version identifier used to verify that a serialized object's sender and receiver agree on the class shape during deserialization.

  • If omitted, the JVM computes one from the class's structure — fragile, changes if fields change
  • Mismatched UID on deserialization → InvalidClassException
  • Always declare it explicitly for any class you intend to persist long-term
transient & non-serializable fields
Modifier / caseEffect
transientField is skipped during serialization, reset to default on deserialization
staticBelongs to the class, not the instance — never serialized
Non-serializable fieldThrows NotSerializableException at runtime unless marked transient
Referenced objects Every non-transient field's type must also be Serializable (recursively) — including collections' contents.

Reading objects (ObjectInputStream)
try (ObjectInputStream in = new ObjectInputStream(
        new FileInputStream("employees.dat"))) {

    Employee e = (Employee) in.readObject();
    List<Employee> all =
        (List<Employee>) in.readObject();

} catch (IOException | ClassNotFoundException e) {
    e.printStackTrace();
}
Read order matters Objects must be read back with readObject() calls in the exact same order they were written — the stream has no labels, only a sequence.
Plain file streams (non-object data)
// Byte-level copy, no serialization involved
try (InputStream in = new FileInputStream("source.bin");
     OutputStream out = new FileOutputStream("dest.bin")) {

    byte[] buffer = new byte[4096];
    int bytesRead;
    while ((bytesRead = in.read(buffer)) != -1) {
        out.write(buffer, 0, bytesRead);
    }
}
