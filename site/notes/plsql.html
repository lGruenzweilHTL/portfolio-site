Oracle PL/SQL Cheatsheet

Block structure
DECLARE                   -- optional: variables, types, cursors
  v_name  VARCHAR2(50);
  v_count NUMBER := 0;
BEGIN                      -- required: executable statements
  v_count := v_count + 1;
  DBMS_OUTPUT.PUT_LINE('Count: ' || v_count);
EXCEPTION                  -- optional: error handlers
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('Error: ' || SQLERRM);
END;
/
The trailing slash ( / ) Tells SQL*Plus / SQL Developer "end of PL/SQL block, execute now" — it's the block terminator, distinct from the ; that ends individual statements inside the block. Required after every standalone block, CREATE OR REPLACE PROCEDURE/FUNCTION/TRIGGER.
Always check USER_ERRORS after deploying After any CREATE OR REPLACE PROCEDURE/FUNCTION/TRIGGER, run SELECT * FROM USER_ERRORS; — compilation errors don't always surface loudly, and a "successfully compiled" object can still be silently broken (status INVALID) if you don't check.

CREATE TABLE anatomy
CREATE TABLE Product (
    Id         NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    EAN        CHAR(13) UNIQUE,
    Descr      VARCHAR2(500),
    CategoryId NUMBER,

    CONSTRAINT FK_Product_ProductCategory
        FOREIGN KEY (CategoryId) REFERENCES ProductCategory(Id)
);
IDENTITY primary key GENERATED BY DEFAULT AS IDENTITY auto-generates the value on insert if none is supplied, but still lets you override it explicitly when needed (unlike GENERATED ALWAYS, which forbids supplying a value at all).

Composite (multi-column) primary & foreign keys

Used when a table's identity is the combination of two (or more) columns — e.g. a junction/link table — or when a foreign key must reference a multi-column primary key elsewhere.

CREATE TABLE ProductsInWarehouse (
    WarehouseId NUMBER,
    ProductId   NUMBER,
    Amount      NUMBER,

    CONSTRAINT FK_ProductsInWarehouse_Product
        FOREIGN KEY (ProductId) REFERENCES Product(Id),
    CONSTRAINT FK_ProductsInWarehouse_Warehouse
        FOREIGN KEY (WarehouseId) REFERENCES Warehouse(Id),
    CONSTRAINT PK_ProductsInWarehouse
        PRIMARY KEY (WarehouseId, ProductId)   -- composite PK
);

-- a FK can reference a composite PK too — column ORDER must match
CREATE TABLE CommissionFromWarehouse (
    WarehouseId  NUMBER,
    ProductId    NUMBER,
    Commissioner VARCHAR2(200),

    CONSTRAINT FK_CommissionFromWarehouse
        FOREIGN KEY (WarehouseId, ProductId)
        REFERENCES ProductsInWarehouse(WarehouseId, ProductId),
    CONSTRAINT PK_CommissionFromWarehouse
        PRIMARY KEY (WarehouseId, ProductId)
);
Column order matters In a composite FOREIGN KEY (A, B) REFERENCES Target(X, Y), column position defines the pairing (A↔X, B↔Y) — not the column names. Always list both sides in the same matching order.
ALTER TABLE — adding constraints after creation
ALTER TABLE Product
    ADD CONSTRAINT C_Product_Descr CHECK (Descr IS NOT NULL);

ALTER TABLE Warehouse
    ADD CONSTRAINT FK_Warehouse_Region FOREIGN KEY (RegionId) REFERENCES Region(Id);

Same CONSTRAINT syntax as inline — just prefixed with ALTER TABLE ... ADD instead of being declared at creation time.

Simple algorithm patterns: sum & product

The classic exam pattern: loop over a range or the digits of a string, accumulating a running sum or product. Always initialize the accumulator before the loop.

-- Sum of 1..n
v_sum NUMBER := 0;
FOR i IN 1..p_n LOOP
  v_sum := v_sum + i;
END LOOP;
-- Product / factorial of n
v_product NUMBER := 1;  -- starts at 1, not 0!
FOR i IN 1..p_n LOOP
  v_product := v_product * i;
END LOOP;
Accumulator starting value Sum starts at 0 (identity for addition); product/factorial starts at 1 (identity for multiplication). Starting a product accumulator at 0 is a very common bug — it zeroes out the entire result on the first multiplication.
CONTINUE (12c+) & labeled loops
<<outer>>
FOR i IN 1..5 LOOP
  FOR j IN 1..5 LOOP
    CONTINUE outer WHEN j = 3;  -- skip remainder of inner; continue outer
    EXIT     outer WHEN i = 4;  -- exit outer loop entirely
  END LOOP;
END LOOP outer;

Handling exceptions
BEGIN
  SELECT name INTO v_name
  FROM   emp WHERE id = 999;
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    v_name := 'Unknown';
  WHEN TOO_MANY_ROWS THEN
    RAISE_APPLICATION_ERROR(
      -20001, 'Multiple rows found'
    );
  WHEN OTHERS THEN
    ROLLBACK;
    RAISE;  -- re-raise to caller
END;
Manually raising a built-in exception

You don't need a user-defined exception to signal "this input is invalid" — raising an existing built-in exception by name is perfectly valid and often expected for input validation:

PROCEDURE check_input(p_val NUMBER) IS
BEGIN
  IF p_val IS NULL OR p_val < 0 THEN
    RAISE VALUE_ERROR;   -- no need to declare it, it's built in
  END IF;
END;

The caller then catches it with a plain WHEN VALUE_ERROR THEN handler — no PRAGMA EXCEPTION_INIT needed (that's only for mapping a custom-named exception to a specific ORA- error code).

CREATE OR REPLACE TRIGGER TR_INSERTUPDATE_PRODUCT_VALIDATE_EAN
BEFORE INSERT OR UPDATE ON Product
FOR EACH ROW
BEGIN
  check_ean13(:NEW.EAN);
  DBMS_OUTPUT.PUT_LINE('check_ean13 passed for Product ' || :NEW.Id);
END;
/

Mutating table error

A FOR EACH ROW trigger that tries to SELECT (or modify) the same table it's defined on raises ORA-04091: table is mutating, trigger/function may not see it.

-- INSIDE a trigger on Product — this fails:
SELECT COUNT(*) INTO v_cnt FROM Product;
Why this matters here Calling an external validation procedure like check_ean13 is safe — it doesn't query the Product table. The trap appears if you try to inline a query against the trigger's own table instead.
Enabling / disabling triggers
ALTER TRIGGER TR_INSERTUPDATE_PRODUCT_VALIDATE_EAN DISABLE;
ALTER TRIGGER TR_INSERTUPDATE_PRODUCT_VALIDATE_EAN ENABLE;

-- disable/enable ALL triggers on a table at once
ALTER TABLE Product DISABLE ALL TRIGGERS;
ALTER TABLE Product ENABLE ALL TRIGGERS;

Useful for bulk-loading data without re-validating every row, then re-enabling afterward.

Worked example: validation algorithm with built-in exception

The exam-style pattern: validate input shape first (length/null checks), then run a simple sum/product algorithm over the digits, then compare a computed result against an expected value — raising a built-in exception on any failure.

CREATE OR REPLACE PROCEDURE check_ean13 (
    p_ean IN Product.EAN%TYPE
)
IS
    v_sum   NUMBER := 0;
    v_digit NUMBER;
    v_check NUMBER;
BEGIN
    -- 1. validate shape first
    IF p_ean IS NULL OR p_ean = '' OR LENGTH(p_ean) != 13 THEN
        RAISE VALUE_ERROR;
    END IF;

    -- 2. accumulate weighted sum over digits 1..12
    FOR i IN 1..12 LOOP
        v_digit := TO_NUMBER(SUBSTR(p_ean, i, 1));  -- non-numeric chars raise VALUE_ERROR here too
        IF MOD(i, 2) = 0 THEN
            v_sum := v_sum + (v_digit * 3);
        ELSE
            v_sum := v_sum + v_digit;
        END IF;
    END LOOP;

    -- 3. compute & compare check digit
    v_check := MOD(10 - MOD(v_sum, 10), 10);
    IF v_check != TO_NUMBER(SUBSTR(p_ean, 13, 1)) THEN
        RAISE VALUE_ERROR;
    END IF;
END;
/

SELECT * FROM USER_ERRORS;
Note the implicit validation TO_NUMBER(SUBSTR(...)) already raises VALUE_ERROR by itself if a character isn't numeric — you don't always need a separate explicit check for that specific case, only for things Oracle won't catch for you (null, wrong length).

USER_TAB_COLUMNS vs. USER_TAB_COLS USER_TAB_COLS includes Oracle's internal/hidden system-generated columns (e.g. for function-based indexes); USER_TAB_COLUMNS filters those out and only shows "real" user-visible columns. When in doubt for a clean column listing, prefer *_TAB_COLUMNS — but know *_TAB_COLS exists, it's an easy trick question.

Resolving foreign keys (incl. composite/multi-column)

A foreign key in USER_CONSTRAINTS doesn't point at a table+column directly — it points at another constraint via R_CONSTRAINT_NAME (the referenced PK/UQ constraint). Get the actual columns from USER_CONS_COLUMNS, joined on that constraint name.

SELECT
    fk.constraint_name AS fk_name,
    fk.table_name       AS fk_table,
    fkc.column_name      AS fk_column,
    pkc.table_name       AS target_table,
    pkc.column_name      AS target_column,
    pkc.POSITION         AS column_position
FROM USER_CONSTRAINTS fk
JOIN USER_CONS_COLUMNS fkc
    ON fkc.constraint_name = fk.constraint_name
JOIN USER_CONS_COLUMNS pkc
    ON pkc.constraint_name = fk.r_constraint_name
   AND pkc.POSITION = fkc.POSITION       -- ← REQUIRED for multi-column FKs
WHERE fk.constraint_type = 'R'
ORDER BY fk_name, fk_column;
The single most common mistake on this query type Joining USER_CONS_COLUMNS only on constraint_name (without matching POSITION) works fine for single-column FKs, but silently produces a cross-product (wrong/duplicated rows) for multi-column FKs like CommissionFromWarehouse (WarehouseId, ProductId). Always match POSITION on both sides when a FK could be composite.
