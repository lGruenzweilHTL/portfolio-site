UML Cheatsheet

Class diagrams · object diagrams · PlantUML syntax

What a class diagram models

A class diagram describes the static structure of a system: classes, their attributes/operations, and the relationships between them — the type level, not any specific runtime state.

Class box notation
┌─────────────────────┐
│       Employee       │  ← class name
├─────────────────────┤
│ - id: int             │  ← attributes
│ - name: String         │
│ # salary: double       │
├─────────────────────┤
│ + raiseSalary(p: int) │  ← operations
│ + getName(): String   │
└─────────────────────┘

Three compartments: name, attributes, operations. Either lower compartment may be omitted if not relevant.

Multiplicity
NotationMeaning

Placed at each end of an association — e.g. Team "1" ── "1..*" Player means one Team has one or more Players.

Read multiplicity at the FAR end The number near a class describes how many instances of that class can be linked to one instance on the other end — not how many of itself it has. This is the single most common exam mistake.
Aggregation vs. composition example
// Composition: Room cannot exist without House
House ◆────── Room

// Aggregation: Player can exist without Team
Team  ◇────── Player
Test Ask: "If the whole is deleted, must the part be deleted too?" Yes → composition. No, it can live on independently → aggregation.
Self-referencing (recursive) associations

A class can have an association to itself — extremely common for modeling sequences, hierarchies, or networks without inventing extra helper classes. Watch for this pattern; it shows up constantly.

PatternMultiplicity shapeUse case
Linked list1 ── 0..1 (e.g. next)Ordered sequence — steps in a recipe, queue items
Tree0..1 parent ── 0..* childrenFile system, org chart, category tree
Graph / network0..* ── 0..*Friend relationships, flight routes
// Recursive sequence (e.g. Arbeitsschritt -> nextStep)
┌────────────────┐
│  Arbeitsschritt  │
├────────────────┤
│ - beschreibung    │
│ - dauer            │
└────────────────┘
        △
        │ self-association
        │
   "1" ──────── "0..1"
   (current)     (next)
Why use recursion instead of a fixed list of attributes A self-reference (e.g. nextStep: Arbeitsschritt) models an arbitrary-length, ordered chain with a single relationship — no need for separate "step1, step2, step3..." attributes, and it naturally supports any number of steps without changing the model.
What an object diagram models

An object diagram is a snapshot of concrete instances at one point in time — actual objects with actual attribute values and actual links between them, rather than the general types and rules a class diagram defines.

Class diagram vs. object diagram Class diagram = the blueprint (what can exist and how it's allowed to relate). Object diagram = one concrete instantiation of that blueprint at runtime (what does exist right now).
Object box notation
┌──────────────────────────┐
│  anna : Employee           │  ← objectName : ClassName, underlined
├──────────────────────────┤
│ id = 7                     │  ← attribute = concrete value
│ name = "Anna Berger"       │
│ salary = 4200.0            │
└──────────────────────────┘

The header is always underlined. The object name is optional (an unnamed instance is written :Employee).

Links between objects

A link is an instance of an association — a concrete connection between two specific objects, drawn as a plain line.

anna : Employee ────── teamX : Team
Recursive associations as object instances

A self-referencing class (e.g. Arbeitsschritt.nextStep) becomes a chain of linked objects in the object diagram — each instance pointing to the next, terminating where the link is absent.

s1 : Arbeitsschritt          s2 : Arbeitsschritt          s3 : Arbeitsschritt
beschreibung = "Sauce kochen"  beschreibung = "Schichten"     beschreibung = "Überbacken"
dauer = 30                    dauer = 10                     dauer = 45

   s1 ───nextStep──▶ s2 ───nextStep──▶ s3 ───nextStep──▶ (none)
Exam tip When a scenario describes "steps in a fixed order" or "a person's manager" or anything chained/hierarchical, expect a self-referencing association in the class diagram — and a corresponding chain of linked objects here. This is your teacher's favorite trick, draw it explicitly rather than listing steps as separate attributes.
Multi-level fan-out example

Object diagrams commonly fan out across several association levels from one root object — e.g. a rental company with customers, who each have contracts, which each reference a vehicle:

v1 : Autovermietung
name = "Antigravity Rental"
        │
        ▼
   k1 : Kunde
   name = "Max Mustermann"
        │
   ┌────┴────┐
   ▼         ▼
m1:Mietvertrag  m2:Mietvertrag
   │                │
   ▼                ▼
p1 : Pkw         l1 : Lkw

Each box is a concrete instance with concrete attribute values; the links mirror the associations from the class diagram, but now connect specific named objects instead of types.

When to use an object diagram
  • To illustrate a complex or non-obvious class structure with a concrete, easy-to-follow example
  • To verify multiplicity constraints by walking through a real scenario
  • To document a specific system state at a particular moment (e.g. for debugging or test-case design)

Reading the arrow The arrowhead/diamond always sits at the "target" side written after the arrow — e.g. in ClassA --|> ClassB, ClassA is the subclass and ClassB is the superclass (arrow points "up" toward the parent).
Abstract classes & interfaces
abstract class Fahrzeug {
  - fahrgestellnummer: String
  - kennzeichen: String
  {abstract} berechnePreis(): double
}

interface Zahlbar {
  + berechnePreis(): double
}

class Pkw {
  - sitzplaetze: int
}

Pkw --|> Fahrzeug
Pkw ..|> Zahlbar

Abstract classes use solid-line generalization; interfaces use dashed-line realization. Both arrowheads are hollow triangles.

Multiplicity & labels
Team "1" -- "1..*" Player : verwaltet >

Multiplicities in quotes sit at each end; the label after : names the relationship, and >/< at the end of the label hints the reading direction.

// layout direction hints, if auto-layout looks wrong
ClassA -u-> ClassB   // up
ClassA -d-> ClassB   // down
ClassA -l-> ClassB   // left
ClassA -r-> ClassB   // right
Self-referencing association syntax

Recursion is written exactly like any other association — both ends just happen to be the same class. Always give the association ends explicit role names so the diagram (and your explanation) stays unambiguous.

class Arbeitsschritt {
  - beschreibung: String
  - dauer: int
}

// linked-list style recursion
Arbeitsschritt "1" -- "0..1" Arbeitsschritt : nextStep >

Tree-shaped recursion (e.g. a category hierarchy) follows the same idea with both a parent and children role:

class Kategorie {
  - name: String
}

Kategorie "0..1" -- "0..*" Kategorie : parent / children >
Full worked example
@startuml
abstract class Fahrzeug {
  - fahrgestellnummer: String
  - kennzeichen: String
  - tagespreis: double
}

class Pkw {
  - sitzplaetze: int
  - kraftstoffart: String
}

class Lkw {
  - ladekapazitaet: double
  - zulassungGewicht: double
}

class Kunde {
  - kundenNr: String
  - name: String
}

class Mietvertrag {
  - mietVertragsNr: String
  - abholdatum: LocalDate
  - rueckgabedatum: LocalDate
  + berechneGesamtpreis(): double
}

Pkw --|> Fahrzeug
Lkw --|> Fahrzeug

Kunde "1" -- "0..*" Mietvertrag : schliesst ab >
Mietvertrag "0..*" -- "1" Fahrzeug : bezieht sich auf >
@enduml
