Git Cheatsheet

Architecture & commands · branching strategies · merge vs. rebase · advanced topics

The three areas

Git tracks file state through three areas as changes move from disk into history.

AreaWhat's in it
Working DirectoryYour actual files on disk — anything edited, untracked, or staged
Staging Area (Index)Changes marked with git add, ready to be committed
Local Repository (.git)Committed history — snapshots reachable from a branch
Remote RepositoryA copy of the history hosted elsewhere (e.g. GitHub) — synced via push/pull/fetch
Distributed VCS Unlike centralized systems (e.g. SVN), every clone holds the full history. There is no single point of failure, and commits can be made fully offline.
Creating & cloning
# create a new local repository
git init

# clone an existing remote repository
git clone <url>
Local workflow
git status                  # what changed?
git add <file>             # stage changes
git commit -m "message"  # snapshot staged changes
git log --oneline          # compact commit history
Syncing with a remote
git pull     # fetch + merge in one step — run at the start of every work session
git fetch    # download remote changes WITHOUT integrating them — lets you inspect first
git push     # upload local commits to the remote
git pull vs. git fetch git pull = git fetch + git merge. Fetch only updates your remote-tracking branches (e.g. origin/main) — your local branch is untouched until you explicitly merge or rebase.
Local user configuration
ScopeApplies to
--localCurrent repository only (default)
--globalAll repositories of the current OS user
# set local credentials (e.g. for a work project)
git config --local user.name  "Your Name"
git config --local user.email "you@example.com"

# show full effective config
git config list

# remove global credentials (e.g. on a shared lab machine)
git config --global --unset-all user.name
git config --global --unset-all user.email
Types of branches
BranchPurpose
Main / ReleaseAlways deployable — formerly called "master"
DevelopIntegration branch for completed features (Git-Flow only)
FeatureOne branch per new feature, merged back when done
BugfixFixes a non-urgent bug
HotfixLike Bugfix, but urgent — usually branched directly off main
Git-Flow workflow

Two permanent branches (main, develop) plus several supporting branches (feature/*, release/*, hotfix/*). Structured and explicit — well suited to scheduled releases.

Use when You need formal release cycles, multiple versions in production, or strict QA gates before release.
GitHub-Flow workflow

Only one permanent branch (main) plus short-lived feature/* and hotfix/* branches, merged via pull request as soon as they're ready. Simpler, faster cadence.

Use when You deploy continuously and don't need to maintain multiple released versions in parallel.
Forks & Pull Requests

To contribute to a repo you don't own, you fork it — a smart copy that keeps a backlink to the original. After committing changes on your fork, you open a pull request asking the owner to merge your changes back in.

Keep your fork synced Before opening a pull request, sync your fork with the upstream original. Working from a stale fork is the most common cause of avoidable merge conflicts.
Forking vs. Templating
ForkCreate from Template
Link to originalMaintained — can pull updates or send PRs backNone — fully independent from creation
Typical useContributing back to a shared projectStarting fresh from a boilerplate (e.g. assignment template)
The core difference
MergeRebase
HistoryPreserved as-is — both branch lines stay visibleRewritten — feature commits are replayed on top of the target branch
Resulting shapeBranching, with a merge commit joining the linesLinear — looks as if the feature was built directly on the latest target branch
Commit hashesUnchangedChanged — rebased commits get new hashes
ContextOriginal chronological context preservedOriginal context can be lost/altered
Merging
git switch feature
git merge main   # bring main's changes INTO feature
# creates a merge commit with two parents
Pro Non-destructive — never rewrites existing commits. Safe on shared/public branches.
Rebasing
git switch feature
git rebase main   # replay feature's commits on top of main
# no merge commit — linear history
Caution Never rebase commits that have already been pushed and shared — it rewrites history and breaks collaborators' clones.
When to use which
  • Use merge on shared/public branches, or whenever you want to keep an accurate record of when branches diverged and rejoined.
  • Use rebase on your own local, not-yet-pushed feature branch to keep a clean linear history before opening a pull request.
  • A common combo: rebase locally to clean up, then merge (often via PR) into the shared branch.
HEAD references
ReferenceMeaning
HEADThe current/latest commit
HEAD~1One commit before HEAD (second-to-last)
HEAD~2Two commits before HEAD
HEAD^The predecessor — same as HEAD~1 for a single-parent commit
HEAD^2Second parent of a merge commit (HEAD^1 = first parent)
git checkout HEAD~1   # check out the second-to-last commit
Cherry picking

Applies a single commit from another branch onto the current branch — without merging the whole branch. Useful when a bugfix landed on an unfinished feature branch.

git switch main
git cherry-pick -x <commit-hash>
-x flag Records the original commit hash in the new commit message — useful for tracing where a cherry-picked commit came from.
.gitignore

Excludes matching files from being tracked — generated/build artifacts (e.g. node_modules/, compiled binaries) and secrets (.env) should never be committed.

Rule of thumb Anything that's generated (compiled, installed) doesn't belong in the repo. Config files, docs, and source code do — except credentials, API keys, or passwords.
