Docker & Kubernetes Cheatsheet

Docker basics · Docker Compose · Kubernetes concepts · Docker vs. Kubernetes

Image vs. container
ImageContainer
What it isRead-only template/blueprint, built in layersA running (or stopped) instance of an image
MutabilityImmutable once builtHas its own writable layer on top of the image
RelationshipOne image →→ many containers can run from it
Layers & build cache Each Dockerfile instruction creates a new image layer. Docker caches layers and reuses them on rebuild if nothing above that instruction changed — order instructions from least-to-most frequently changing (e.g. dependency install before source copy) for faster builds.
Dockerfile instructions
InstructionPurpose
FROMBase image to build on — every Dockerfile starts with this
ARGBuild-time-only variable, not available in the running container
ENVEnvironment variable available at build time AND inside the running container
WORKDIRSets the working directory for subsequent instructions
COPYCopies local files/dirs from the build context into the image
ADDLike COPY, but also fetches from URLs and auto-extracts local tar archives
RUNExecutes a command at build time (e.g. install dependencies) — creates a new layer
USERSwitches to a non-root user for subsequent instructions / the running container
EXPOSEDocuments which port the app listens on (doesn't actually publish it)
VOLUMEDeclares a mount point for persistent data
HEALTHCHECKDefines how Docker checks container health
CMDDefault command/args when the container starts (overridable at docker run)
ENTRYPOINTFixed executable for the container — not normally overridden
# Dockerfile
FROM node:18
ARG BUILD_ENV=production
ENV NODE_ENV=$BUILD_ENV
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
USER node
CMD ["node", "index.js"]

# build it
docker build -t my-app .
CMD vs. ENTRYPOINT
CMDENTRYPOINT
RoleDefault command/argumentsFixed executable the container always runs
Overridable?Yes — replaced by args after docker run image <args>No — those args get appended to it instead
# Combined: ENTRYPOINT fixed, CMD = default args
ENTRYPOINT ["python"]
CMD ["app.py"]
# docker run image        -> python app.py
# docker run image other.py -> python other.py
Bind mounts vs. named volumes
Bind mountNamed volume
Maps toAn exact host filesystem pathA Docker-managed internal location
VisibilityHost changes appear instantly in containerIsolated from the host filesystem
Best forLocal dev / hot-reloadingProduction data (DB storage etc.) — more portable & performant
docker run -v $(pwd):/app ...        # bind mount
docker run -v db_data:/var/lib/postgresql/data ...  # named volume
Container lifecycle & basic commands
docker build -t <name> .   # build an image from a Dockerfile
docker run <image>        # start a NEW container
docker start <name|id>    # restart a stopped container
docker stop <name|id>     # gracefully stop a running container
docker exec -it <id> /bin/bash  # open a shell inside a running container
docker container ls -a   # list all containers (running + stopped)
docker image ls           # list local images
Pushing to a registry
docker tag my-image ghcr.io/<user>/<repo>:latest
docker push ghcr.io/<user>/<repo>:latest
.dockerignore

Excludes files/folders from the build context (e.g. .git/, node_modules/, *.log) → faster builds, smaller images, no secrets leaking into the image.

Starting & stopping
docker compose -f compose.yaml up       # foreground, attached
docker compose -f compose.yaml up -d    # detached / background
docker compose -f compose.yaml logs -f # follow logs
CommandEffect
docker compose stopStops containers, keeps them + their volumes/data
docker compose downStops and removes containers, networks (volumes kept unless -v)
Environment variables

Used to keep credentials/config out of the image and adjustable per-environment (dev/test/prod) without rebuilding.

services:
  db:
    image: postgres:18
    environment:
      POSTGRES_DB: db
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
Health checks

Lets dependent services wait until a container (e.g. a database) is actually ready, not just "started".

db:
  image: postgres:18
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U app"]
    interval: 5s
    retries: 5
app:
  depends_on:
    db:
      condition: service_healthy
Core resource types
ResourcePurpose
PodSmallest deployable unit — one or more containers sharing network & storage
DeploymentManages a Pod's lifecycle: desired replica count, container image, rollout/rollback strategy, health checks
ReplicaSetEnsures N replicas of a Pod exist — usually managed indirectly via a Deployment, rarely created directly
ServiceStable network endpoint (IP/DNS name + port) that load-balances traffic across matching Pods
IngressRoutes external HTTP(S) traffic into the cluster, to different Services based on host/path
NodeA physical or virtual machine in the cluster that runs Pods
NamespaceLogical partition for grouping/isolating resources (e.g. per team or environment)
ConfigMapNon-secret configuration data, injectable as env vars or mounted files
SecretSensitive configuration data (credentials, keys) — base64-encoded at rest, not encrypted by default
Volume / PersistentVolumeClaimStorage attached to a Pod; a PVC requests storage that persists independently of the Pod's own lifecycle
Imperative vs. declarative management
ImperativeDeclarative
HowRun commands directly, e.g. kubectl create deployment ...Define desired state in a YAML manifest, apply with kubectl apply -f ...
DefinesThe path to the goal stateOnly the target state — Kubernetes figures out how to get there
ReproducibilityHarder to version / reproduceEasy — manifest is the source of truth, version-controllable
Annotated manifest example
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webshop-deployment
spec:
  replicas: 3                          # 3 Pod instances are started
  selector:
    matchLabels:
      app: webshop
  template:
    metadata:
      labels:
        app: webshop                  # label the Service will match on
    spec:
      containers:
      - name: webshop-app
        image: ghcr.io/my-org/webshop:v1.2.0  # registry / org / image:tag
        ports:
        - containerPort: 8080
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15      # wait 15s after start before first check
          periodSeconds: 10            # then check every 10s
---
apiVersion: v1
kind: Service
metadata:
  name: webshop-service
spec:
  type: ClusterIP
  selector:
    app: webshop                      # <- must match the Deployment's Pod labels above
  ports:
  - port: 80          # Service's own port, reachable by other apps in-cluster
    targetPort: 8080  # forwarded to this port on the matched Pods
How the Service finds its Pods The Service's spec.selector is matched against the labels under the Deployment's spec.template.metadata.labels — not the Deployment's own top-level metadata. Any Pod carrying a matching label receives traffic from the Service, regardless of which Deployment created it.
Liveness probe failure A check counts as healthy only if the HTTP response status is in the 200–399 range (or times out → unhealthy). On failure, the kubelet kills the container and restarts it — this is Kubernetes' self-healing in action.
Pods & containers within a pod

Multiple containers in one Pod share the same network (localhost) and storage volumes.

  • Sidecar container — supports the main app (logging shipping, TLS termination, config sync) without modifying the app's code
  • Init container — runs to completion before the main app container starts, e.g. to wait for a dependency or seed config
Liveness vs. readiness probes
ProbeChecksOn failure
LivenessIs the container still alive?Kubelet kills & restarts the container
ReadinessIs it ready to receive traffic?Removed from Service endpoints — no restart
Different layers, not competitors

Docker / Docker Compose runs containers on a single server — if that server goes down, the whole app is offline, and there's no scaling across machine boundaries. Kubernetes is a container orchestration tool for distributed, multi-node clusters — it manages and monitors containers across many physical/virtual servers.

Docker (+ Compose)Kubernetes
ScopeSingle hostCluster of multiple nodes
UnitContainerPod (one or more containers)
Self-healingRestart policies per container onlySelf-Healing: failed containers/nodes are automatically rescheduled onto healthy nodes
ScalingManual / limitedHorizontal Autoscaling: Pod count auto-adjusts based on CPU/RAM load
UpdatesManual recreate, brief downtimeRolling Updates & Rollbacks: zero-downtime gradual updates, auto-rollback on failure
Config modelMostly imperative CLI / Compose fileDeclarative manifests as the standard approach
Three key production advantages of Kubernetes Self-Healing, Horizontal Autoscaling, and Rolling Updates & Rollbacks — these are the headline reasons K8s is chosen over plain Docker for production workloads.
